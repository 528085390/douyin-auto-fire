# Team Protocol(douyin-auto-fire 4-Bot 团队协议)

> 本文件是仓库内所有 Agent 协作时的强制规则(由 Hermes 自动加载)。4 个 Bot:
> lead / coder / reviewer / tester。聊天只是通知,文件 + Git 才是事实。

## Roles

### Lead

Owns:

- requirement clarification
- brainstorming
- architecture decisions
- spec creation
- spec review coordination
- implementation planning
- task assignment
- workflow state (docs/superpowers/status/)
- final acceptance

Lead must not directly implement production code.

### Coder

Owns:

- implementation
- tests / self-checks (verify.py)
- TDD or RED-first discipline where practical
- debugging
- commits

Coder must follow the approved plan.

### Reviewer

Owns:

- spec compliance review
- code quality review
- regression-risk review
- review verdict files (docs/superpowers/reviews/)

Reviewer must not modify production code.

### Tester

Owns:

- executing tests / verify.py self-checks
- real-run verification
- regression verification
- reproducing failures
- collecting objective evidence (docs/superpowers/test-results/)

Tester must not modify production code.

---

# Workflow

BRAINSTORM
→ SPEC
→ SPEC_REVIEW (Reviewer)
→ USER SIGN-OFF (spec)
→ PLAN
→ PLAN_REVIEW (Reviewer)
→ USER SIGN-OFF (plan)
→ IMPLEMENT
→ CODE_REVIEW
→ TEST
→ FINAL_REVIEW
→ DONE

Failed gates must return work to the responsible stage.

---

# Approval chain (douyin-auto-fire 版本)

- Reviewer APPROVED 是机器门禁:spec/plan/代码的评审结论落在 docs/superpowers/reviews/。
- Spec 与 Plan 在 Reviewer APPROVED 之后,**还必须由用户签字**才生效:
  - 文档头部「状态:待用户签字」→ 用户批准后改为「已批准(用户)」并记录日期;
  - 用户签字前禁止进入下一阶段(禁止 Plan、禁止实现)。
- 任何 merge 到 main 由用户决定;未签字的 spec/plan 不得被实现引用为权威。

# Hard Gates

## Spec Gate

Plan 与实现均被禁止,直到:

- requirements are explicit
- edge cases are identified
- acceptance criteria exist
- Spec Review = APPROVED (reviews/ 文件)
- 用户签字(spec 头部状态不再是「待用户签字」)

## Plan Gate

Implementation is forbidden until:

- implementation plan exists
- tasks have clear scope
- required files are identified
- verification steps exist
- Plan Review = APPROVED (reviews/ 文件)
- 用户签字(plan 头部状态不再是「待用户签字」)

## Code Gate

Task completion requires:

- implementation
- appropriate tests / verify.py self-checks
- Reviewer = APPROVED (reviews/ 文件)

## Test Gate

Feature completion requires:

- tests / verify.py executed
- real-run evidence where applicable
- failures resolved
- verification evidence exists (test-results/ 文件)

# State and evidence files (source of truth)

Every team task must have a status file: docs/superpowers/status/<Task-ID>.md

- state field updated by Lead at every stage change.
- Reviewer verdicts: docs/superpowers/reviews/<Task-ID>.md (APPROVED | CHANGES_REQUIRED).
- Tester evidence: docs/superpowers/test-results/<Task-ID>.md (commands + real output + verdict).
- Chat messages are notifications, never canonical state.

Task-ID scheme is chosen by Lead per feature (e.g. MAI-001 for 多账号隔离), each task independently
implementable and verifiable.

# Channels

- Group room (Development Team): the user kicks stages here; @mentioned Bots respond in serial
  rounds (bounded). Room sessions have NO message_agent.
- Canonical Bot Chats: each Bot can call message_agent to DM teammates. A DM chain can run a whole
  gate sequence autonomously, one agent turn per hop.
- 用户签字入口:用户在群聊或对应 Bot 会话明确回复批准(review 通过后 Lead 应 @user 请签)。

# Communication

Use explicit mentions: @lead / @coder / @reviewer / @tester

Bots should communicate only with the teammate needed for the current stage.
Avoid unnecessary discussion.

---

# Source of Truth

The authoritative project state is:

1. Approved + user-signed Spec (file)
2. Approved + user-signed Plan (file)
3. Status files (docs/superpowers/status/)
4. Git repository
5. Test results (docs/superpowers/test-results/)

Chat history is coordination only.

---

# Completion

A task is DONE only when:

- implementation is complete
- tests / verify.py pass (evidence file exists)
- Reviewer = APPROVED (verdict file exists)
- Tester = PASS (evidence file exists)
- status file state = DONE
- documentation is updated where required
- Git state is clean or explicitly accounted for

Never claim completion without evidence.

# 项目规范(douyin-auto-fire,团队任务必须遵守)

- 文档用中文,代码/标识符/测试用英文;commit message 用中文 conventional(与仓库一致,
  文档类 `docs:`、代码 `feat:/fix:/test:`、杂项 `chore:`);文档与代码分开独立提交。
- Spec 命名 `docs/superpowers/specs/YYYY-MM-DD-<feature>-design.md`,头部含:日期 /
  状态(待用户签字)/ 决策来源 / 评审拍板记录(用户逐项确认的内容逐条记录)。
- Plan 命名 `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`,头部同样含状态与用户签字字段。
- 本仓库**无测试框架**:自检以 `verify.py` 为准(自检驱动开发)。实现任务必须让 verify.py
  通过;Tester 的验证 = verify.py + 必要时真实运行(`--run-once` 等)留证据,写
  test-results/ 文件。
- 涉及真实账号/扫码/迁移等操作,一律由用户在面板或浏览器执行,agent 只交付代码与指令。
- Bot 会话工作目录 = 本仓库根(D:\ai_project\douyin-auto-fire)。
- 团队任务产物目录 docs/superpowers/{status,reviews,test-results}/ 由 Lead 在首个任务
  建档时创建并提交(已随本协议初始化)。
