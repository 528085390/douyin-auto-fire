# 工作原理与架构

本文档说明项目内部如何工作，便于排查问题与二次开发。

---

## 一、模块划分

| 文件 | 职责 |
| --- | --- |
| `main.py` | 命令行入口：交互菜单、`--run-once` / `--setup-login` / `--test`、非交互 `HH:MM`；以及把时间/内容/目标写回 `config.yaml` 的函数（`update_schedule_time` / `update_message_texts` / `update_targets`）。 |
| `douyin.py` | **自动化核心**：`DouyinStreak` 类封装浏览器启动、登录态、IM 导航、会话匹配与切换、消息发送、风控检测、审计截图、会话扫描。 |
| `panel.py` | 本地管理面板 HTTP 服务（纯标准库）：提供静态页面、API、定时任务注册/管理、运行记录存储与裁剪、前后台触发调度。 |
| `panel.html` | 面板前端页面（原生 JS，无框架），调用 `/api/*`。 |
| `config.yaml` | 全部可配置项。 |

核心流程：`panel.py` / `main.py` → 构造 config dict → 实例化 `DouyinStreak(cfg)` → `run()`（前台触发）/ `setup_login()`（仅登录）/ `scan()`（扫描会话）。

---

## 二、单次运行数据流（`DouyinStreak.run()`）

```
run()
 ├─ needs_verify = False
 ├─ verify_wait = 0(后台) / 120(前台可见)   # 前台下验证后保持窗口等用户手动解除
 ├─ 若无 targets → 直接返回
 ├─ _open_browser()            # 启动持久化浏览器上下文
 ├─ _ensure_login()            # 未登录则提示/等待扫码
 ├─ _check_risk_stop()         # 进入前先查一次风控
 │     └─ 命中 → needs_verify=True，返回
 └─ for idx, target in targets:        # 逐个目标
       ├─ _check_risk_stop()           # 发送前/中复检风控
       ├─ _open_conversation(target)   # 进 IM 浮层 → 匹配并点击会话
       └─ _send_text(text, name)       # 校验当前会话 → 填字 → 回车发送 → 截图
       └─ 目标间随机等待 15~45 秒（降低风控）
 └─ finally: _close_browser()
```

返回前设置 `needs_verify`；面板据此把状态标记为 `needs_verify` 并提示用户手动处理。

---

## 三、浏览器与反指纹

- 使用 **Playwright 持久化上下文**（`launch_persistent_context`），登录态落在 `browser.user_data_dir`（默认 `./browser_data`），重启浏览器无需重新登录。
- 可选 `channel: "chrome"` 使用本机 Chrome，指纹比自带 Chromium 更正常。
- `real_chrome_profile: true` 可复用真实 Chrome 目录（需先关闭在用 Chrome）。
- 启动前通过 `add_init_script` 注入 **stealth 反指纹脚本**（去掉 `navigator.webdriver` 等自动化痕迹）。
- 视口固定 `1280×900`，`locale=zh-CN`。

---

## 四、IM 导航：只走首页「消息」浮层

按设计，**全程在抖音首页的「消息」浮层里操作私聊/群聊**，不访问独立的 `/im/` 页面。

- `_navigate_to_im()`：在首页点「消息」入口打开右侧浮层；且**幂等**——浮层已打开时不会重复点击（避免把浮层又关掉）。
- `_wait_im_list_ready()`：列表显示「加载中」时持续等待，最多 2 分钟。
- `_try_switch_to_chat_tab()`：确保当前停在「私信/聊天」列表 tab（某些版本默认停在「互动/通知」）。
- **严格禁止使用搜索框**匹配会话，避免把消息误发到搜索栏；匹配范围限定在左侧会话列表容器内。

---

## 五、会话校验：几何探测（核心）

早期版本依赖 class 名在 DOM 上判断「当前打开了哪个会话」，在真实抖音 DOM 上极易失效（把首页推荐视频作者当成会话名，或完全读不到标题），导致「明明点开了却找不到会话」的误判。现已改为 **几何探测**。

### `_PROBE_JS`（在页面内执行的探测脚本）

综合四个几何/语义信号，返回结构化结果：

1. **会话列表容器边界**：通过 `conversationConversationListwrapper` / `ConversationListwrapper` / `conversationList` / `LeftPanelboxList` 等 class 定位左侧列表容器，取其矩形范围。
2. **聊天输入框**：选取可见的 `contenteditable` / `textarea`，**排除 placeholder/aria-label 含「搜索」或 class 含 `search` 的搜索框**，记录其矩形。
3. **标题候选**：在「输入框正上方、同列、且位于浮层范围内」的近叶子节点里，收集文本作为标题候选（过滤掉导航噪声关键字：消息/推荐/关注/充钻石/客户端…）。
4. **左侧列表选中态**：扫描 `class` 含 `active/selected/current/checked` 的列表项作为第二信号。

### `_chat_panel_probe(name)`

执行 `_PROBE_JS(name)`，返回 `{hasInput, title, candidates, activeItems, hasName, nameInActive, inputRect, listRect}`。`_active_conversation_name` 与 `_conversation_is_open` **共用同一结果**，避免两个函数各自判断互相矛盾。

### `_conversation_is_open(name, probe)`

- 若 `probe.hasName`（标题候选含目标名）→ 通过；
- 或 `probe.nameInActive`（左侧选中项含目标名）→ 通过；
- 否则若 `probe.title` 含目标名 → 通过；
- 否则判定未打开。

## 六、三态发送判定（`_send_text`）

发送前再校验一次当前右侧聊天面板确实打开的是目标会话，避免发错人。采用**三态**而非简单二元，防止「读不到」被当成「切错了」而误伤：

- **A. 探测到目标名** → 校验通过，正常发送。
- **B. 探测到别的会话名** → 确认切错，留审计证据后**重切**；重切后仍是别人 → 抛错跳过（不发错人）。
- **C. 什么都探测不到** → 输入框已找到说明确有会话打开，保守放行并留审计证据（否则一条都发不出去）。

发送动作：点击聊天输入框 → 按字输入 → 回车（`Enter` 即发送）→ 若输入框仍残留文字再补点「发送」按钮 → 发送后截图 → 再次复检风控。

---

## 七、人工兜底（manual fallback）

自动匹配不到会话时（列表滚动后仍点不到），脚本会：

1. 留审计截图与 JSON（见下）；
2. 暂停 `browser.manual_select_sec`（默认 30 秒），提示用户手动点击目标会话；
3. 时间到后再探测一次：若已手动点开则继续；仍失败则留 `manual_timeout` 审计证据。

---

## 八、审计机制（`_audit_dump`）

所有失败/异常路径（点击失败 `click_fail`、未匹配 `no_match`、手动超时 `manual_timeout`、切错会话 `wrong_conversation`、重切仍错 `reswitch_wrong`、探测为空 `probe_empty` / `reswitch_probe_empty`）都会调用 `_audit_dump(tag, name)`，产出两份证据：

- **截图** `NNN_HHMMSS_audit_<tag>.png`（可在执行记录里直接查看）；
- **JSON** `audit_<tag>_<HHMMSS>.json`，含：
  - `probe`：标题候选、左侧选中项、输入框/列表矩形；
  - `page.nameHits`：页面上所有出现目标名的可见叶子节点（判断「页面到底有没有这个名字」）；
  - `page.listItems`：**限定在会话列表容器内**的真实列表项（避免抓到首页推荐视频，这是早期误判的根因之一）。

同时把一行摘要写入日志，便于一眼看出是「**真找不到**」（列表项里确实没有目标名）还是「**误判**」（列表里有、但校验逻辑没读到）。

---

## 九、风控检测与优雅停手

`_detect_risk_control()` 遍历**所有 frame**（验证常渲染在独立 iframe，主页面可能为空），检查：

- 文案命中：`请完成下列验证后继续`、`拖动完成拼图`、`滑动验证`、`安全验证` 等关键词；
- URL 命中 `captcha` / `nocaptcha` / `verifycenter` / `geetest` / `bscap` 等，**且该框架确实渲染了内容**（排除抖音预加载的不可见种子 iframe 误判）。

一旦命中：`verify_wait=0`（后台）立即停手；`verify_wait=120`（前台可见）先保持浏览器打开、每隔几秒轮询，验证解除则继续，超时仍未解除才停手。停手后 `needs_verify=True`，本次运行标为「需验证」，**绝不尝试自动拖动滑块/破解验证码**。

---

## 十、拟人操作

- `_human_move`：鼠标带随机抖动的曲线轨迹移动；
- `_human_click`：按下-松开有时差；
- `_human_type`：逐字输入，节奏 70~170ms 随机，偶尔停顿「思考」；
- 目标间随机等待 15~45 秒。

---

## 十一、运行记录存储与裁剪

- 每次运行在 `runs/` 下生成独立目录：
  - `<id>.json` 元数据（开始/结束时间、状态、目标、错误）；
  - `<id>.log` 完整日志；
  - `<id>/` 目录：证据截图（打开会话、发送后 `after_send`、各审计节点 `audit_*`）。
- `prune_runs(keep=3)`：**只保留最近 3 条**，更早的连同元数据、日志、截图目录一并彻底删除，不留残留。面板每次启动和每次运行结束都会裁剪一次。
- 会话列表扫描结果持久化在 `conversations_cache.json`，重启面板后仍能显示上次扫描到的会话。

---

## 十二、并发模型

- 面板用全局锁 `_run_lock` 保证**同一时刻只有一个浏览器任务**（`_current_run`）。「触发运行」「打开浏览器」「选会话同步」三者互斥（共用 `user_data_dir` 锁）。
- 触发运行在后台守护线程 `_worker` 中执行，实时进度通过 `progress_callback` 回传面板首页步骤条；结束后**无论如何都会释放锁**（含异常分支），避免「任务已结束但面板仍显示运行中」。
- 提供 `/api/run-reset`、`/api/login-reset` 作为状态卡死时的兜底。
