# 工作原理与架构

本文档说明项目内部如何工作，便于排查问题与二次开发。

---

## 一、模块划分

| 文件 | 职责 |
| --- | --- |
| `main.py` | 命令行入口 + **账号层**：账号原语（`account_root` / `list_accounts` / `create_account` / `validate_alias` / `load_user_data` / `save_user_data` / `update_*`）、旧数据迁移（`legacy_pending` / `migrate_legacy_to_account`）、跨进程运行守卫（`acquire_run_guard` / `release_run_guard`）、`load_config(alias=None)` 双入口、CLI（交互菜单 / `--account` / `--migrate` / `--list-accounts` / `--run-once` / `--setup-login` / `--test`）。把时间/内容/目标写回**当前账号**的 `userdata/accounts/<别名>/user_data.yaml`。 |
| `douyin.py` | **自动化核心**：`DouyinStreak` 类封装浏览器启动、登录态、IM 导航、会话匹配与切换、消息发送、风控检测、审计截图、会话扫描。**多账号下零改动**——浏览器目录由 `load_config(alias)` 覆盖注入（发送核心与目录解耦）。 |
| `runner.py` | 定时任务专用入口：解析 `--account`，经 `panel.trigger_run(texts, headless=None, account=…)` 与面板「一键触发」合流；轮询 `panel._load_meta(run_id, account)`。 |
| `panel.py` | 本地管理面板 HTTP 服务（纯标准库）：静态页面、API、定时任务注册/管理（按账号任务名）、运行记录存储与裁剪（按账号目录）、前后台触发调度（进程内锁 + 跨进程守卫）、账号解析统一入口 `_resolve_account`。 |
| `panel.html` | 面板前端页面（原生 JS，无框架）：账号栏（切换/添加/迁移引导/空态）+ 三页签，`api()` 封装自动附带当前账号调用 `/api/*`。 |
| `config.yaml` | 公开配置（浏览器、日志、面板端口）；账号私有项在 `userdata/accounts/<别名>/user_data.yaml`。 |

核心流程：`panel.py` / `runner.py` / `main.py` → **解析账号**（`_resolve_account` / `resolve_account`）→ `load_config(alias)`（合并账号私有键 + 覆盖 `browser.user_data_dir` 指向账号目录）→ 实例化 `DouyinStreak(cfg)` → `run()`（前台触发）/ `setup_login()`（仅登录）/ `scan()`（扫描会话）。

### 账号目录布局（MAI-001）

```
userdata/
├── .running                      # 跨进程运行守卫（独占文件：{account, pid, start_ts}，运行结束 finally 删除）
├── accounts/<别名>/              # 每个账号一个目录（别名 1~24 位英文/数字/下划线）
│   ├── user_data.yaml            #   targets / message / schedule（私有键）
│   ├── browser_data/             #   登录态（cookie），DouyinStreak 持久化目录
│   ├── conversations_cache.json  #   会话列表缓存
│   └── runs/                     #   执行记录：<id>.json（含 account 字段）+ <id>.log + 截图目录
├── panel_state.json              # {last_account: 别名}（面板记忆，gitignored）
├── run.log / panel.log           # 基础设施日志（全局，不进账号目录）
└── （旧顶层 user_data.yaml / browser_data / runs / conversations_cache.json 迁移后清空）
```

## 二、单次运行数据流（`DouyinStreak.run()`）

```
入口（面板触发 / runner 定时 / CLI 手动）
 ├─ 解析账号（动作路径必须显式/唯一，否则拒绝——防串号）
 ├─ 进程内锁检查（面板）→ acquire_run_guard(account)  # O_EXCL 独占创建 userdata/.running
 │     └─ 被占（含陈旧 pid 自愈后仍被占）→ 报「账号 X（pid Y）正在运行中」，本次跳过
 └─ _worker(run_id, texts, headless, account)          # 后台守护线程
run()
 ├─ needs_verify = False
 ├─ verify_wait = 0(后台) / 120(前台可见)   # 前台下验证后保持窗口等用户手动解除
 ├─ 若无 targets → 直接返回
 ├─ _open_browser()            # 启动持久化浏览器上下文（user_data_dir = 账号目录）
 ├─ _ensure_login()            # 未登录则提示/等待扫码
 ├─ _check_risk_stop()         # 进入前先查一次风控
 │     └─ 命中 → needs_verify=True，返回
 └─ for idx, target in targets:        # 逐个目标（当前账号的 targets）
       ├─ _check_risk_stop()           # 发送前/中复检风控
       ├─ _open_conversation(target)   # 进 /chat 会话列表 → 匹配并点击会话
       └─ _send_text(text, name)       # 校验当前会话 → 填字 → 回车发送 → 截图
       └─ 目标间随机等待 15~45 秒（降低风控）
 ├─ finally: _close_browser()
 └─ finally: 写回 meta（含 account）→ update_message_texts(account,…) → prune_runs(account,3)
             → 释放进程内锁 → release_run_guard()     # 守卫与 _current_run 同一 finally
```

返回前设置 `needs_verify`；面板据此把状态标记为 `needs_verify` 并提示用户手动处理。

## 三、浏览器与反指纹

- 使用 **Playwright 持久化上下文**（`launch_persistent_context`），登录态落在 `browser.user_data_dir`——多账号下由 `load_config(alias)` **强制覆盖**为 `userdata/accounts/<别名>/browser_data`（整体 gitignore），每账号一份登录态、物理隔离，重启浏览器无需重新登录。
- 可选 `channel: "chrome"` 使用本机 Chrome，指纹比自带 Chromium 更正常。
- ⚠️ `real_chrome_profile: true` **与多账号隔离互斥，必须保持 `false`**：该键为真时会用真实 Chrome 登录态目录**替换**账号级 `user_data_dir`，两个账号共用同一份登录态（正是串号场景）。
- 启动前通过 `add_init_script` 注入 **stealth 反指纹脚本**（去掉 `navigator.webdriver` 等自动化痕迹）。
- 视口固定 `1280×900`，`locale=zh-CN`。
- 已知局限（组合一）：两号仍同设备同指纹同出口 IP，靠错峰 ≥15 分钟 + 低频私信 + 绝不并发降险。

## 四、IM 导航：直达 /chat 独立页

抖音改版后 IM 独立成单页，首页不再有「消息」浮层入口。改版前依赖「点消息浮层」的链路整条失效，现改为**直接 `goto https://www.douyin.com/chat`** 取代旧链路。

- `_goto_chat()`：直达 IM 独立页，等待 `[data-e2e="conversation-item"]`（或列表容器）出现即视为就绪。
- `_is_logged_in()`：在 /chat 上双向判定——出现会话项/列表容器即已登录；出现 `#login-panel-new` / `#douyin_login_comp_flat_panel` 即未登录。
- **严格禁止使用搜索框**匹配会话，避免把消息误发到搜索栏；匹配范围限定在左侧会话列表容器内（精确等值）。

## 五、会话校验：确定性语义锚点（核心）

抖音改版后 IM 独立成 `https://www.douyin.com/chat` 单页，会话项带有稳定语义埋点，不再需要几何推断。导航直接 `goto /chat` 取代「首页点消息浮层」。

### 会话项枚举与匹配

- 会话项锚点：`[data-e2e="conversation-item"]`，标题读 `.conversationConversationItemtitle`（DOM 文本完整，不含省略号）。
- 群/私聊判别：头像节点互斥——`img.commonConversationIconnoDrag` 命中即群聊，否则私聊。
- 匹配采用**精确等值**（会话名在 DOM 里始终完整，左侧列表是纯群名，无省略号、无前缀匹配）。虚拟列表只渲染可视区，故边滚边找，连续 3 屏无新 `data-index` 视为到底。

### `_conversation_is_open(name)`

双信号校验，任一命中即通过：

- 信号 A：左侧该会话项带选中态 class（含 `curConversation`）且标题等于目标名；
- 信号 B：右侧标题 `.RightPanelHeadertitle` 去 `(人数)` 后缀后等于目标名。

两个都读不到即判未打开——锚点确定后读不到就是真没打开，放行只会发错人。

## 六、发送强校验（`_send_text`，决策 1B）

发送前先确认当前打开的正是目标会话（否则记 `wrong_conversation` 并跳过），再点击编辑器输入内容：

发送动作：点击聊天输入框 → 按字输入 → **确认文字进入编辑器（经 `_editor_text_equals` 与发送内容等值比对；失败自动重试一次，再失败审计 `type_fail` 并跳过该目标）** → 回车（`Enter` 即发送）→ 若输入框仍有残留再补点「发送」按钮 → **铁证：输入框已清空** → 气泡回读仅作附加信心 → 截图 → 复检风控。发送内容为空/纯空白属配置错误，在入口直接拦截，不进入发送流程。

发送成功判定（2026-09-04 spec 4.1）由两级证据构成，缺一不可：

- **前置（无条件）**：文字真实进入编辑器——经 `_editor_text_equals(text)` 与发送文本等值（比较规则收窄只改该方法体）。空真防护：若打字从未落地，编辑器全程为空，则「清空」判定恒真、会漏发误报成功，故必须先断言落地；
- **铁证（无条件）**：发送动作后编辑器已清空——`textContent` 剥掉零宽字符 `\u200b` 后为空。

`browser.strict_verify=true` 时在上述双证据之外再附加气泡文本比对（最后一条 `isFromMe` 容器文本包含发送内容），失配只告警并按成功降级处理，截图命名 `sent_soft_` 前缀（不截审计件，不谎报失败）；`false` 时跳过该气泡比对（文字落地 + 清空仍强制）。

## 七、审计机制（`_audit_dump`）

所有失败/异常路径（未匹配 `no_match`、切错会话 `wrong_conversation`、点到了但没切过去 `switch_fail`、找不到编辑器 `no_editor`、文字没进输入框 `type_fail`、发送后输入框仍有残留 `send_fail`）都会调用 `_audit_dump(tag, name)`，产出两份证据：

- **截图** `NNN_HHMMSS_audit_<tag>.png`（可在执行记录里直接查看）；
- **JSON** `audit_<tag>_<HHMMSS>.json`，含：
  - `probe.active`：右侧当前打开的会话名（去后缀）；
  - `probe.items`：**限定在会话列表容器内**的真实列表项（标题 / 类型 / 是否当前选中），用于比对名字差异；
  - `probe.editor` / `editor_text_len`：输入框是否可见、文本长度（只记长度，不落发送内容）；
  - `page.nameHits`：页面上所有出现目标名的可见叶子节点（判断「页面到底有没有这个名字」）。

同时把一行摘要写入日志，便于一眼看出是「**真找不到**」（列表项里确实没有目标名）还是「**误判**」（列表里有、但校验逻辑没读到）。

## 八、风控检测与优雅停手

`_detect_risk_control()` 遍历**所有 frame**（验证常渲染在独立 iframe，主页面可能为空），检查：

- 文案命中：`请完成下列验证后继续`、`拖动完成拼图`、`滑动验证`、`安全验证` 等关键词；
- URL 命中 `captcha` / `nocaptcha` / `verifycenter` / `geetest` / `bscap` 等，**且该框架确实渲染了内容**（排除抖音预加载的不可见种子 iframe 误判）。

一旦命中：`verify_wait=0`（后台）立即停手；`verify_wait=120`（前台可见）先保持浏览器打开、每隔几秒轮询，验证解除则继续，超时仍未解除才停手。停手后 `needs_verify=True`，本次运行标为「需验证」，**绝不尝试自动拖动滑块/破解验证码**。

## 十、运行记录存储与裁剪

- 每次运行在**所属账号**的 `accounts/<别名>/runs/` 下生成独立目录：
  - `<id>.json` 元数据（开始/结束时间、状态、目标、错误、**account 字段**）；
  - `<id>.log` 完整日志；
  - `<id>/` 目录：证据截图（打开会话、发送后 `after_send`、各审计节点 `audit_*`）。
- `prune_runs(account, keep=3)`：**每账号只保留最近 3 条**，更早的连同元数据、日志、截图目录一并彻底删除，不留残留；只清该账号目录，不误删他号记录。面板每次启动逐账号裁剪、每次运行结束裁剪当前账号。
- run_id 时间戳全局唯一；面板查看明细/截图时按 meta 的 `account` 字段**反查**归属账号目录（`_find_run_account`），切号后点开旧记录仍指向原账号，不跨号猜。
- 会话列表扫描结果持久化在该账号的 `conversations_cache.json`；面板内存镜像带归属账号（`_conversations_account`），切号/读取/保存前强制按账号重载（`_ensure_conversations_for`），杜绝 A 号列表被展示或保存进 B 号。

## 十一、并发模型（进程内锁 + 跨进程守卫）

- **进程内**：面板用全局锁 `_run_lock` 保证同一时刻只有一个浏览器任务（`_current_run` + `_current_run_account`）。「触发运行」「打开浏览器」「选会话同步」三者互斥；另一账号在跑时，本账号页面的触发类按钮同样置灰（文案「账号 X 正在运行中」）。
- **跨进程（MAI-001 硬机制）**：`userdata/.running` 守卫文件——`acquire_run_guard(account)` 以 `O_CREAT|O_EXCL` 独占创建（内容 `{account, pid, start_ts}`），runner 定时任务 / 面板一键触发 / CLI 手动（含 `--setup-login` 登录窗口、`--migrate` 迁移）三路共用；被占时报「账号 X（pid Y）正在运行中」并跳过本次。每账号一条独立 schtasks = 独立进程，进程内锁管不住跨进程并发，守卫是「同一时刻绝不并发」（风控纪律）的机制保证。
- **获取顺序**：进程内锁检查 → 守卫获取 → 起线程；守卫获取失败时尚未持有任何需释放的资源，直接返回，无「守卫已获但早退」的残留窗口。
- **释放**：守卫一律在 worker/窗口的 `finally` 中与进程内锁一起释放（`release_run_guard()`），异常分支也不会漏。
- **陈旧自愈**：上次进程崩溃留下 `.running` 时，下次获取会读其中 pid 并用 `tasklist /FI "PID eq <pid>"` 探测存活；pid 已不存在 → 视为残留删除后重试一次（不永久锁死）；pid 存活才拒绝。`/api/run-reset`、`/api/login-reset` 只重置进程内锁，不删守卫（跨进程语义由 pid 探测兜底）。
- 触发运行在后台守护线程 `_worker` 中执行，实时进度通过 `progress_callback` 回传面板首页步骤条；结束后**无论如何都会释放锁与守卫**（含异常分支），避免「任务已结束但面板仍显示运行中」。
